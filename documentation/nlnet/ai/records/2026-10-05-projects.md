### 1. Context

Archiyou lets anyone publish a script as a configurator
(`/configurators/{author}/{name}:{version}`). Nothing supports what happens *after* someone
configures something: receiving an order request, keeping that exact configuration, revising
it, sending an offer with frozen outputs, and seeing whether the client reacted. The browser
already has a disabled `projects` stub (`apps/editor/src/pages/browser.ts` `_sections()`,
`packages/ui/src/browser/browser-header.ts` "Project (coming soon)").

Goal: a simple, complete Projects area for **professionals**. A professional is any
signed-in user who runs projects: the author of a configurator, or someone using another
author's configurator for their own client (a dealer, an architect). A professional:
- receives product orders from their configurators;
- adds configurations of any script or configurator to a project (immutable snapshots,
  v1..vn) and keeps client information;
- sends **deliveries** by email link: an offer with a frozen 3D model, documents and sheets;
- sees what the client did: opened, downloaded, accepted, or sent changes.

Decisions (owner, 2026-10-05/06):
- **Access:** every signed-in user with a verified email. No entitlement gate, so email
  sending must be abuse-proof.
- **Projects are not tied to authorship.** Anyone can start a project from any
  script or configurator. A signed-in user viewing a configurator gets *Add to project*.
- **Configurator offers either downloads or *Order product*.** Each fulfillment gets a
  category: `download` (the Download menu, one row per output bundle and format) or
  `product` (an *Order product* button that sends an order request to the configurator's
  author).
- **Offer content in v1:** the script's own outputs, frozen: documents as PDF and sheets
  as XLSX (tables and metrics, e.g. a price table). On top come offer fields: total,
  currency, valid until, note. No uploaded PDFs, no line-item editor.
- **3D in a delivery:** frozen at send time and shown in a light viewer page (no CAD
  kernel). An optional *Adjust this design* opens the configurator at the delivered
  values; the client's changes come back into the project.
- **No automatic link expiry for now.** Links stay valid until the professional revokes
  them.

Research basis:
- **Handoff from a configurator:** the visitor's saved configuration travels with their
  contact details (ShapeDiver model states, Threekit saved configurations, Roomle *Request
  product*, Zakeke *Get a quote*).
- **Lead forms:** a lead form creates the contact and the project at an "Inquiry" stage
  (Dubsado, HoneyBook).
- **Quotes:** immutable once sent; a revision supersedes; acceptance binds to one exact
  revision (Salesforce CPQ, HubSpot, Jobber).
- **Deliveries:** the transmittal model (Autodesk Docs): an immutable package, a secure
  link, no account needed.
- **Analytics bar:** opened / opens / downloads / response, with the sender's own previews
  not tracked (PandaDoc, DocSend, Qwilr).
- **EU privacy:** no open pixels (Apple Mail Privacy Protection fires them anyway), no
  cookies on recipient pages. Use cookieless first-party events with a hashed IP and a
  daily salt, 12-month retention, and ≥128-bit revocable link tokens.

### 2. Verified constraints

- **The server never runs scripts** (execution off by default, unsandboxed). Deliverables
  are made in the professional's browser by the existing fulfillment code
  (`apps/editor/src/services/fulfillment.ts`: `fulfillmentExports`, `outputsToFiles`) and
  uploaded:
  - docs are requested as `svg-pages` and painted to PDF;
  - the GLB comes back as an `ArrayBuffer`;
  - tables and metrics already export `xlsx` (`packages/core/src/execution/types.ts`;
    output paths `default/tables/*/xlsx` and `default/metrics/*/xlsx`; the mime type is in
    the `fulfillment.ts` format table).
- **The client page needs no CAD kernel.** `<model-viewer>.load(ArrayBuffer)` renders a
  standalone GLB (`packages/ui/src/viewer/model-viewer.ts`). No
  `apps/editor/src/state/*.ts` imports `execution-service`, and only
  `layouts/layout-main.ts` warms the worker, so a page outside `layout-main` loads three.js
  but never the ~26 MB kernel.
- **Projects store snapshots, not references.** Unversioned script rows are overwritten by
  autosave coalescing (`ScriptStore.saveVersion`, 10 min). Published rows are immutable in
  code and params. Published code is readable by anyone the configurator is public to, so
  a professional's browser can run someone else's configurator to generate files.
- **Param values validate** with `Script.fromData(d).checkParamValuesVerbose(values)`
  (`packages/core/src/Script.ts`): it uppercases keys, fills defaults and throws on unknown
  names (catch → 422).
- **"Open" must not import.** `importScriptFromData` always creates a new `-imported` file
  (`state/core.ts`); using it to open would recreate the tutorial-copies clutter.
- **Fulfillments today** (`packages/core/src/ScriptSchema.ts`
  `ScriptPublishedFulfillmentSchema`): `{ name, description?, exports, delivery: 'anonymous
  download' | 'email' | 'pay', price? }`. The Download menu blocks `email`/`pay` as "Not
  available yet" (`packages/ui/src/configurator/configurator-download-menu.ts`).
- **Templates to copy:**
  - public POST + store + tests: `routes/feedback.ts`, `FeedbackStore.ts`,
    `tests/unit/feedback.test.ts` (`memory://` PGlite, bare Fastify);
  - raw-body uploads: the `image/png` parser in `plugin.ts`, `ThumbnailStore`,
    `api.putBinary()`;
  - email: `EmailService` (fixed Reply-To, one-CTA template, dev fallback logs, never
    throws).
- **House rules:**
  - no foreign keys;
  - user identity is the username handle (`request.user.sub`);
  - new on-disk data goes under `./data` and into `config.ts` `backupTargets` (tables are
    covered by `pg_dump`);
  - migrations: edit `schema.ts`, run `pnpm db:generate`, commit the SQL and the journal.

### 3. Terms

| Term | Meaning |
|---|---|
| Professional | The signed-in user a project belongs to (column `professional`, a username handle). Not necessarily the script's author. |
| Author | The user who wrote and published the script or configurator. |
| Configurator | A published script version. Its fulfillments are downloads and/or product orders. |
| Fulfillment category | `download`: the Download menu, as today. `product`: an *Order product* button. |
| Request | A project in status `request`, created when a visitor orders a product. It belongs to the configurator's author. |
| Client | A person or company of a professional, deduped on `(professional, lower(email))`. |
| Project | `P-012`: title, client, status, notes, configurations, deliveries, activity. |
| Configuration v1..vn | An immutable snapshot (script + validated values + units + language + thumbnail). |
| Delivery | An immutable package for one configuration: frozen files (GLB, PDFs, XLSX), a message, optional offer fields, a secure link. |
| Offer | A delivery with offer fields (total, currency, valid until, note). |
| Activity | The project's event log. |

### 4. Flows

**Author (publishing)**
1. In `<publish-script-menu>` (and when editing via *Manage configurators*), each
   fulfillment gets a **category**: *Download* (output bundle and formats, as today) or
   *Product order*. A product fulfillment has a name (e.g. "Order this table"), a
   description, an optional indicative price, and `exports`, which preselect the outputs
   when a delivery is made for such an order.

**Professional**
1. **Inbox:** Browser → Projects → *Requests (3)* → `P-012`: the order message, the
   ordered product (fulfillment name), configuration v1 (thumbnail, changed values) and
   the client card → *Start project* (→ `active`) or *Decline* (→ `lost`).
2. **Add to project:** from any configurator (own or not, signed in) or from the editor
   (own script or a shared read-only one), → pick or create a project. The current script
   and param values become configuration v(n+1).
3. **New delivery** from a project:
   - pick the configuration and outputs: the 3D model always, plus documents (PDF) and
     sheets (XLSX). For another author's script, the outputs are limited to what its
     Download fulfillments already give every visitor;
   - fill in the offer fields, the message and the recipient (taken from the client), and
     whether *adjusting* is allowed;
   - *Send*: the browser generates and uploads the files, the server freezes them and
     emails the link (Reply-To = professional).
4. **Follow-up:** deliveries show *sent · opened 2× · downloaded · accepted*. A dot marks
   projects with new client activity. Mark the project won or lost, archive it, or revoke a
   link.

**Client (no account)**
1. **Ordering:** on a configurator with a product fulfillment, *Order product* (labelled
   with the fulfillment name) → name, email, phone (optional), message → "Sent. {author}
   will get back to you." The order lands as a request in the author's Projects.
2. **Delivery page:** the email "{professional} sent you an offer: {title}" links to
   `/d/{token}`:
   - professional, title and message;
   - the 3D viewer, documents and sheets;
   - an offer box with *Accept* / *Decline* / *Request changes* (+ note).
3. **Adjusting:** *Adjust this design* opens the configurator at the delivered values.
   *Send changes* adds configuration v(n+1) (`origin='adjust'`) to the **same** project of
   the professional who sent the delivery, and emails them.
4. **Revoked link:** "This link is no longer available."

### 5. Data model (`apps/server/src/db/schema.ts`, one migration `0001_projects.sql`)

`text` uuid ids, `timestamptz`, `jsonb`, no FKs. Every query filters `professional`.

**clients**: `id`, `professional`, `email` (lowercased), `name`, `company`, `phone`,
`address`, `note`, `created`, `updated`. Unique `(professional, email)`, index
`(professional, updated)`.

**projects**: `id`, `professional`, `number` int (per professional, shown as `P-001`),
`title`, `client_id?`, `status` (`request | active | won | lost`), `note`, `archived_at?`,
`client_activity_at?`, `seen_at?`, `created`, `updated`. Unique `(professional, number)`,
index `(professional, status, updated)`.
- Numbering: `max(number)+1` in the insert transaction; retry once on a unique violation.
- Transitions: `request → active | lost`, `active → won | lost`, `won | lost → active`.
  Archive is independent.
- Unread dot: `client_activity_at > seen_at`. Client events set `client_activity_at`;
  `GET /projects/:id` sets `seen_at`.

**configurations**: `id`, `professional`, `project_id`, `rev` int (1..n), `label?`,
`script` jsonb `ScriptData` snapshot (code, params, presets, units, name, author, fileId,
id, version, published without `translations`), `values` jsonb (full validated set),
`unit_system?`, `lang?`, `thumbnail?`, `origin` (`order | added | adjust`),
`fulfillment?` (product fulfillment name, for orders), `source_version_id?`,
`source_delivery_id?`, `message?`, `created`. Unique `(project_id, rev)`. Immutable except
`label`.

**deliveries**: `id`, `professional`, `project_id`, `configuration_id`, `number` (per
project), `title`, `message` (≤ 2000), `offer` jsonb `{total, currency, validUntil?, note?}
| null`, `recipient_email`, `recipient_name`,
`files` jsonb `[{name, kind: model|document|sheet, bytes, mime}]`, `bytes`, `token` (32
random bytes, base64url, set on send), `status` (`draft | sent | revoked`), `allow_adjust`,
`sent_at`, `first_opened_at`, `open_count`, `download_count`, `response`
(`accepted | declined | changes`, set once), `response_note`, `response_at`, `created`,
`updated`.
- Unique: `token`, `(project_id, number)`. Index `(professional, sent_at)` for send caps.
- No expiry: the link lives until revoked. `validUntil` is offer information shown to the
  client and does not block the link.
- Nothing changes after send except revoke, the counters and the response.

**events**: `id`, `professional`, `project_id`, `delivery_id?`, `configuration_id?`, `type`,
`actor` (`professional | client`), `meta` jsonb, `visitor?`, `created`. Indexes
`(project_id, created)` and `(created)` (for retention).

### 7. Files and storage

- `apps/server/src/services/DeliveryFileStore.ts` (new, ~120 lines) stores files under
  `{config.deliveries.path}/{professional}/{deliveryId}/{name}`, default
  `./data/deliveries`, via tmp+rename.
- Names must match `[a-zA-Z0-9._-]{1,80}`. Extensions and kinds: `.glb` (model), `.pdf`
  (document), `.xlsx` (sheet), `.png` (preview). The mime type is fixed by the extension
  (the table in `fulfillment.ts`); the client's claim is never trusted.
- Files are served only through `/d/:token/files/:name` (no static mount), so revocation
  always applies. Headers: `nosniff`, `private, no-store`; XLSX is always sent as an
  attachment.
- Caps (`SERVER_DELIVERY_*`): 25 MiB per file (octet-stream `bodyLimit`), 60 MiB per
  delivery, 2 GiB per professional.
- `backupTargets` += `{ name: 'deliveries', path: config.deliveries.path, kind: 'dir', optional: true }`.

### 9. Analytics and privacy

- **Events:** `order.received`, `configuration.added`, `status.changed`, `delivery.sent`,
  `delivery.revoked`, `delivery.opened`, `file.downloaded {file}`,
  `delivery.accepted | declined | changes_requested`, `adjust.opened`,
  `adjust.requested {changed: [param names]}`.
- **Who writes them:** the server routes that cause them. The only client-posted type is
  `adjust.opened`. A request carrying the delivery professional's own JWT records nothing.
- **Visitors:** `visitor = sha256(ip + ua + daily salt)`, only to count unique opens. No
  cookies, no pixel, no stored IP.
- **Retention:** events are purged after 365 days (`SERVER_EVENTS_RETENTION_DAYS`), on boot
  and daily.
- **Client page footer:** "{professional} sees when this page is opened and files are
  downloaded. No cookies."
- **Professional view:** per delivery: sent · first opened · opens · downloads · response,
  plus the project timeline. No charts.

### 10. Abuse controls (every verified user can email strangers)

**Delivery sending**
- Verified email is required for every professional mutation; the configurator's *Add to
  project* asks an unverified user to verify first.
- One recipient per delivery. From is always Archiyou; Reply-To is the professional.
- Send caps per professional, counted on `deliveries.sent_at` (no Redis): 10 per hour, 50
  per day. Accounts younger than 24 h: 5 per day. Over the cap → 429.
- Limits: title ≤ 120 chars, message ≤ 2000 chars, sent as escaped text. Links in the
  professional's text are never clickable in our mail.

**Links and files**
- Tokens: 256-bit, revocable (no automatic expiry).
- Delivery files: extension allowlist, size caps and a per-professional quota; writable
  only while the delivery is a draft.
- Another author's script: the delivery can carry only the 3D model and the outputs of that
  configurator's Download fulfillments, the same files any visitor can download. The
  server checks the requested output kinds against the snapshot's `published.fulfillments`.

**Public order form**
- Rate limit: 10 per 10 minutes per IP, and 200 per day per configurator.
- Honeypot: a filled `website` field gets a 200 but nothing is stored.
- Dedupe: the same `(versionId, email, values hash)` within 10 min lands on the same
  project.
- Values are validated (422 on bad ones); the thumbnail is checked as a PNG ≤ 512 KiB.
- Orders are accepted only for an existing `product` fulfillment of a published version
  whose author is verified; anything else returns 404.

**Data isolation**
- The client page never exposes the client's email.
- Professionals never see each other's data, and a foreign ID returns 404.

  - unknown or `download` fulfillment, or an unverified author → 404;
  - honeypot → 200 with nothing stored;
  - duplicate within 10 min → same project; daily cap → 429; bad values → 422;
  - the author email goes through the dev fallback.
- `deliveries.test.ts`:
  - draft → files: bad extension or oversize is rejected; `.xlsx` is accepted;
  - send sets the token; files are refused after send;
  - caps → 429; an output kind not allowed for a foreign script → 422;
  - an open counts, but not for the professional's JWT; unknown token → 404; revoked → 410;
  - downloads count; respond works once (second → 409).
- Phase 4: an adjust adds rev n+1 to the delivering professional's project with the changed
  names; `adjust.opened` is the only client event type; purge respects retention.
- Core: fulfillment schema accepts `category` and a missing `delivery`; old payloads still
  validate.

**Frontend:** `pnpm --filter @archiyou/editor typecheck:own` and the editor and ui tests.

**Manual end-to-end** on the local stack (`pnpm docker:dev`, `pnpm dev`; without Mailgun the

   - *Accept* → the project shows "opened 1× · accepted" plus the unread dot;
   - the professional's own preview did not count.
