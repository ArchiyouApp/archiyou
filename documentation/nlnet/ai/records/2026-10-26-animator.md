## Plan (agent output, reviewed by the human before implementation)

## Animations: an `animator` module, baked glTF clips, and a recorder

### Context

Archiyou wants to show a parametric model as motion, for social media and for the websites
that embed a configurator: the cut stock flying from its stacks into the assembly, a parameter
sweeping from its minimum to its maximum, a turntable, an assembly played step by step. Two
deliverables come out of one description:

- a **GLB with animations**, which plays in the Archiyou viewer, in the configurator embed, in
  Blender and in `<model-viewer>`;
- a **video, GIF or PNG sequence** rendered from it, in the sizes the social platforms want.

This plan proposes five things, in dependency order:

1. an `animator` module in core: animations declared in the script (keyframes, layouts,
   visibility, colour, opacity, a camera), resolved to plain data, baked into the model's GLB;
2. **standard animations** (presets) for any model, with no script code at all;
3. viewer playback with a timeline, and an **Animation tool** in the editor;
4. a **recorder**: deterministic off-screen rendering to WebM, MP4, GIF or PNG frames;
5. **parameter keyframes**: the script run N times with different values, the results merged
   into one GLB.

Two rules run through all of it. **Nothing runs unless asked**: a script that never names
`animator` pays nothing, a run that is not asked for an animation computes none, and no library
is loaded before the feature that needs it is used. **The work happens on a branch `animator`**
off `develop` (§9), in its own worktree (`/mnt/data/dev/archiyou/archiyou-animator`) so the
uncommitted configurator work on `develop` stays where it is.

Every claim about existing code below was checked against the source; the line numbers are
of the `develop` branch on 2026-10-26.

### Decisions

- **Nothing runs unless asked.** `animator` is a lazy getter on the scope: no instance and no
  code until a script names it (the scope is applied with `with (scope)`, `Runner.ts:1115`, so a
  getter fires only on use; `createScope()` :436 builds nothing for it). Declaring records plain
  data. Resolving (layouts, OBBs, refs) and baking happen only when an output asks for that
  animation (`?animations=…`), once per run. The default run bakes no animation and computes no
  preset: the editor's run and the server's default GLB are unchanged. Core gets no new
  dependency; `resolve.ts` and `presets.ts` are a dynamically imported chunk (as `Layouter.ts:321`
  imports `GLTFBuilder`); the Animation tool's panel, `renderModelAnimation()` and the encoders
  load on demand (`await import()`, the `fulfillment.ts:379` and `thumbnails.ts:69` pattern); the
  viewer's pointer plugin is inert for files without the extension.
- **An animation is a time-varying deviation from the finished scene.** The instruct rule
  (`INSTRUCT.md` §1), applied to time: an animation holds poses and style changes keyed by scene
  path and **never mutates the scene**. Layouts go through `Layouter.result()`, never `apply()`.
- **One animation = one glTF clip + one `extras.animations[i]` block**, with chapters inside
  it where there are steps. Not N clips (same argument as `INSTRUCT.md` §9: a list of unnamed
  clips, nothing to scrub).
- **Portable where glTF can say it, extras where it cannot.** Translation, rotation, scale and
  a camera are channels. Visibility is a scale channel with STEP interpolation (plays in every
  viewer) **and** a track in extras (so our viewer hides the object instead of scaling it).
  Colour and opacity are **`KHR_animation_pointer` channels on the part's material**
  (`baseColorFactor` carries both, as RGBA), listed in `extensionsUsed` and never in
  `extensionsRequired`: a viewer without the extension loads the file and plays the motion.
  Our viewer reads them through a small loader plugin (§5); Babylon.js plays them; three.js and
  so `<model-viewer>` ignore them; Blender's glTF add-on writes them behind its "Animation
  Pointer" export option and its import is to be verified when stage 1 lands. The same keys are
  in `extras.animations` for the tool.
- **Animations are entities, not pipelines.** A pipeline makes *another model from the model*
  (a drawing, a cut plan: `help/guide/en/modeling/pipelines.md`). An animation is *the same
  model over time*. It is declared like a doc, a table or a metric, listed in `ScriptMeta`, and
  exported through the model category as a glb option (`default/model/glb?animations=flyin`),
  the way `?instruct=` is: **no new output category**. An animation *of a pipeline's output* is
  left for later (`.pipeline('drawings')` would be the obvious verb).
- **Core bakes, the host renders.** The worker has no renderer, so video is made in the
  browser from the GLB, like a PDF is painted on the main thread from `svg-pages`
  (`fulfillment.ts:17`) and like thumbnails are rendered from the run's GLB. The server stays
  without a headless browser (`plans/SOCIAL_CARDS.md`, "Not doing").
- **Parameter keyframes run in the host.** A run cannot re-run itself with other values; the
  editor or the CLI runs the script per frame and `GLTFBuilder` merges the GLBs. The script
  *declares* the sweep, the host *executes* it — the pattern of `managedParams` and presets.
- **Standard animations are presets of the same API**, not a second code path. They replace
  the hardcoded `ANIMATION_DEFS`.
- **Instructables feed the same baker.** `addInstruct()` becomes "InstructData → AnimationData"
  plus the generic baker. `extras.instruct` and the viewer's step player do not change.
- **No cursor in the API.** Every verb takes its target and its time explicitly, as `Step` does
  and for the reason its header gives.

### 1. The data model

What a script writes is resolved to this and nothing else. The glTF baker, the viewer and the
recorder read `AnimationData`; the Animation tool shows it.

```ts
// packages/core/src/animator/types.ts
interface AnimationData
{
    name: string
    title?: string
    duration: number                           // seconds
    loop: 'none' | 'loop' | 'pingpong'
    tracks: Array<TrackData>                   // one per scene path the animation touches
    camera?: CameraTrackData                   // optional: the file carries a camera node too
    chapters?: Array<{ title: string, tStart: number, tEnd: number }>   // from instruct steps
    params?: ParamTrackData                    // present on a parameter sweep (§6)
    preset?: { kind: PresetKind, options: Record<string, any> }         // how it was made
}

interface TrackData
{
    path: string                               // SceneNode.path()
    /** Poses as rigid transforms ABOUT THE PART'S OWN CENTRE — the StepPlacement convention
     *  (instruct/types.ts), which both the glTF node and the three.js object can apply. */
    pose?: Array<{ t: number, position?: Vec3, rotation?: Quat, scale?: Vec3, easing: Easing }>
    visible?: Array<{ t: number, value: boolean }>
    opacity?: Array<{ t: number, value: number, easing: Easing }>
    color?: Array<{ t: number, value: string, easing: Easing }>       // '#rrggbb'
}

interface CameraTrackData
{
    kind: 'keys' | 'turntable'
    keys?: Array<{ t: number, position: Vec3, lookAt: Vec3, easing: Easing }>
    turntable?: { degrees: number, axis: 'z', elevation: number }     // relative to the current framing
    projection: 'orthographic' | 'perspective'
}

interface ParamTrackData
{
    frames: Array<Record<string, any>>         // param values per frame, in order
    fps?: number
}
```

`Easing` is the existing `LayoutAnimationInterpolation` (`modeler/types.ts:45`). Times are
seconds on the animation's own timeline. A track that is absent means "where the model has it".
The `color` and `opacity` keys of one track bake into one RGBA channel on the part's material (§4).

### 2. The script API

An `animator` module next to `annotator` and `interactor` (`ArchiyouModules`, `types.ts:25`;
`Runner._addModulesToScopeState()` :503-518 defines it as a **getter** that makes the `Animator`
on first use; `RESERVED_SCOPE_NAMES`, `ModuleRegistry.ts:38` gets `'animator'`), dropped per run
where `docs.reset()` is called (`Runner.ts:1507`).

```js
// A standard animation, with its defaults
animator.preset('flyin');

// The same, tuned: start laid out as stacks of stock, end as modelled
animator.create('flyin')
    .duration(4)
    .from('partstack', { spacing: 60 })        // a Layouter kind: 'partstack' | 'row' | 'exploded'
    .order('bottomUp')                          // parts arrive lowest first: 'bottomUp' | 'stack' | 'scene'
    .stagger(0.08)                              // each part leaves a little after the previous one
    .easing('easeOut')
    .turntable(90);                             // the camera turns a quarter while it happens

// Explicit keyframes: a rigid pose at a time, about a pivot (default: the part's own centre)
anim = animator.create('swing').duration(2).loop('pingpong');
anim.key(0, door, { rotation: [0, 0, 0],  pivot: hinge });
anim.key(2, door, { rotation: [0, 0, 95], pivot: hinge }, 'easeInOut');
anim.key(1, handle, { move: [0, 0, -20] });                   // relative to the modelled position

// Visibility, colour, opacity. References as in instruct: a Shape, a collection, a part
// label ('A', 'A#2') or a layer/group name ('frame').
anim.hide('B', 0).show('B', 1);
anim.fade('frame', 0, 1, { opacity: [0, 1] });
anim.highlight('A', 1, 2, 'orange');                          // colour for a while, then back

// A camera path, or just a turntable
anim.camera(0, 'front').camera(2, [-1, -1, 1]);              // the instruct camera forms
animator.preset('turntable', { degrees: 360, duration: 8 });

// An instructable as an animation: its steps become chapters
animator.create('assembly').steps('assembly');

// A parameter sweep. The host runs the script once per frame (§6)
animator.create('widths')
    .param('WIDTH', { from: 400, to: 800, frames: 9 })
    .duration(3).loop('pingpong');
```

Rules the `Animation` class enforces at resolve time, with the message the author needs:

- declaring is free: every verb stores its raw arguments; nothing is resolved, laid out or baked
  until an output asks for the animation (§4);
- a key at a time outside `[0, duration]` throws with both numbers;
- an unknown part label throws with the valid labels, as `Instruct._unknownRef()` :428 does;
- `from()` and `key()` on the same part are allowed; the later key wins where they overlap;
- `param()` makes the animation **host-executed**: in a single run it resolves to its
  declaration only, and the GLB of that run carries no clip for it (the tool says why).

`rotation` is Euler degrees `[x, y, z]` or a quaternion `[x, y, z, w]`; `pivot` turns it into
the placement form: `position = R·(c − pivot) + pivot`, rotation `R` about `c`.

Shared with instruct, extracted rather than duplicated: `resolveRef()` and `_shapesOf()`
(`Instruct.ts:367, 439`) move to `packages/core/src/modeler/refs.ts`; `_runLayout()` /
`_placements()` (:1028, :1105) move to `Layouter` as `placementsOf(result)` so both callers get
the centre-based form from one place.

### 3. Standard animations

`animator.preset(kind, options?)` is `animator.create(kind).…` with chosen defaults. The
editor offers them for any model with no script code, and a script can pin their options. A
preset is computed only when an output names it; none is computed implicitly.

| Preset | What it does | Defaults |
|---|---|---|
| `flyin` | parts start in `partStack` stacks beside the model and fly to where the model has them, staggered | 3 s, `easeOut`, `order:'bottomUp'`, stagger so the last part leaves at 60 % of the duration |
| `exploded` | the model comes apart along the explode rays and back | 2 s, `pingpong`, `easeInOut` |
| `turntable` | the camera orbits the model; nothing moves | 360°, 8 s, loop, elevation of the current view |
| `build` | parts appear one after another in `bottomUp` order, each dropping in from above over a short distance | 0.25 s per part, visibility STEP + a short move |
| `assembly` | the first instructable of the script, steps as chapters | its own timeline |
| `layout` | today's `rowOrtho` row | kept so `?animations=1` keeps meaning `exploded` + `layout` |

Two things the layouts need for this that they do not have:

- **a place to put the stock.** `rowOrtho()` and `partStack()` start their row at `x = 0`,
  which is on top of the model. `PartStackLayoutOptions` / `LayoutViewOptions` get an
  `origin?: PointLike`; the `flyin` preset puts the stacks on the ground (z = 0) to the −X side
  of the model's bbox, one spacing away.
- **an order.** `partStack` orders by quantity; a fly-in that reads as building wants the
  lowest parts first. The order is a preset option resolved in core (`bottomUp` = authored
  centre z, then x), not a Layouter concern.

### 4. Resolution and baking in core

#### `Animator` and `Animation`

`packages/core/src/animator/Animator.ts` (the module: `create()`, `preset()`, `animations()`,
`get()`, `reset()`, `toData()`), `Animation.ts` (the fluent class, raw arguments only),
`resolve.ts` (raw → `AnimationData`, the only place that touches the scene, through
`Layouter.result()` and the shared refs), `presets.ts`, `types.ts`.

Resolution is lazy and cached per run, as `Instruct._resolve()` is: a `partStack` costs an
OBB per solid and `exploded` iterates collisions, so a preset is computed once per run however
many outputs ask for it, and never when none does: the default GLB (`animations: false`)
resolves nothing. `resolve.ts` and `presets.ts` are loaded with `await import()` from the export
path, as `Layouter.ts:321` loads `GLTFBuilder`, so a run that bakes nothing does not parse them.

#### The generic baker in `GLTFBuilder`

`addAnimationData(data: AnimationData)`:

- **pose tracks**: per node, one translation and one rotation channel (scale when any key has
  one), hold-then-ease sampling generalised from `_addInstructTranslation()` /
  `_addInstructRotation()` to keys `{t, value, easing}` for any target path. **The pose is
  sampled as one rigid transform**: at every sample the eased position, slerped rotation and
  scale are combined into the node's `translation = authored + position − R·S·centre`, so a
  part's centre travels the straight line it is given while it turns, and a rotation is eased
  like a translation (17 samples, or 25 for `spring`, also for a `linear` move that turns).
  The previous bakers interpolated translation and rotation apart — the instruct one with two
  linear keys per turn — so a turning part swung off its path.
- **the layout pivot fix**: `addAnimations()` wrote a Layouter rotation straight onto the
  container node, which sits at the world origin, while the kernel turns a shape about its own
  bounding-box centre (`Mesh.rotateQuaternion()` keeps the centre, `Layouter._applyTransforms()`
  then translates). Every turned part of the `layout` clip therefore orbited the origin. Layouts
  now go through `Layouter.placementsOf(result)` (centre `c`, `position = c + translation`,
  rotation about `c`: what `Instruct` read off its copies, without copying), and the baker
  writes them as above. Pinned by a test; the `exploded` clip, which never turns, is unchanged.
- **visibility**: a scale channel, STEP interpolation, `1 ↔ 1e-4`, on the **geometry nodes**
  (the mesh children) of the track's subtree, not on the container: the container's scale
  channel stays free for the pose, and a layer hidden while one of its parts is hidden too is
  one STEP channel per mesh with the visibilities combined. Not zero: a singular matrix makes
  three.js's normal matrix NaN; `1e-4` is invisible and stays invertible. Our viewer plays the
  same channel, so it needs no visibility code of its own.
- **camera**: one node `${name}-camera` with translation and rotation keys
  (`_lookAtQuaternion()`), orthographic or perspective as the data says. A turntable is
  realised as 36 keys per full turn at a distance from the bbox, like `_addInstructCameras()`
  sizes its cameras. Separate cameras per instruct step stay as they are.
- **colour and opacity**: one `KHR_animation_pointer` channel per material, pointer
  `/materials/{i}/pbrMetallicRoughness/baseColorFactor`, VEC4 samples (RGB from the colour keys,
  A from the opacity keys, each held and eased like a pose), `target.path = 'pointer'` and no
  target node. The material's `alphaMode` becomes `BLEND` when any alpha key is below 1; a part's
  edge material (`material_edge`, meshup `GLTFBuilder.ts:1282`) gets the same alpha so edges fade
  with their faces. `highlight()` is colour keys; an `emissiveFactor` pointer for a glow is a
  one-line addition once the first channel works. Materials are found per scene path like nodes
  (`_materialsByScenePath()` next to `_nodesByScenePath()`: the container's geometry children,
  one material per shape).
- **the extension class**: gltf-transform has no `KHR_animation_pointer`, so it is written as the
  other glTF-less extensions are (`BentleyLineStyleExtension`, meshup `GLTFBuilder.ts:286`):
  `AnimationPointerExtension extends Extension` with an `AnimationPointerProperty` (`material`,
  `pointer`) set on the `AnimationChannel` (an `ExtensibleProperty`). Its `write()` runs after
  `json.animations` exists (core 4.3.0 writer, index.modern.js:5647 then :5684) and fills
  `channels[k].target.extensions.KHR_animation_pointer.pointer` from `context.materialIndexMap`
  and `context.animationIndexMap`; `read()` does the reverse for round trips. `setRequired(false)`,
  always. It lives in core (`animator/AnimationPointerExtension.ts`), not next to its siblings in
  meshup: meshup is a separate repository (a submodule), and core's `GLTFBuilder` is the only
  writer of animations. Every IO the builder makes registers it, so a GLB read back keeps it.
- **extras**: `addData({ animations: [...data] })`, next to `instruct`.

Then the two existing entry points become thin:

- `addAnimations(layoutResults)` :269 → `layoutToAnimation(result, options)` + the baker.
  The sample-count tests (`GLTFBuilder.animations.test.ts`) keep holding because the baker
  uses the same `_createAnimationProgressSamples()`.
- `addInstruct(data)` :451 → `instructToAnimation(InstructData)` (poses from
  `placements`/`move` exactly as `_instructTrack()` computes them, chapters from the steps) +
  the baker + `_addInstructCameras()` + `addData({ instruct })`. `GLTFBuilder.instruct.test.ts`
  pins that the clip, its channels and `extras.instruct` are unchanged.

Delete the commented flipbook at :164-217 (its replacement is §6) and `exportToSVGAnimation()`.

#### Where the glTF tree can and cannot follow

A pose track names a container node; the viewer's path map keys the same node. A part that is
not a part (a curve, a vertex) still has a container and can move, hide or fade; it just
cannot be a stack. A layer named in `hide()` hides its subtree — intended for a layer, and
the reason `instruct-playback.isPart()` exists for the viewer's own hiding.

### 5. Playback in the viewer and the Animation tool

#### `model-viewer`

Public API, next to the instruct one (:1413-1488):

- `animations(): Array<AnimationData>` — from `state.animations`, else `extras.animations`,
  else bare clip names (a foreign GLB).
- `playAnimation(name, { loop?, speed?, from? })`, `pauseAnimation()`, `seekAnimation(t)`,
  `stopAnimation()` (puts everything back), `animationTime()`.
- an `animation-time` event per rendered frame while playing or scrubbing, for the scrubber.
- `followCamera(on)`: while on, the camera node's transform drives `_camera` and the orbit
  controls are disabled; off restores the controls' target. Default off in the editor, on in
  the recorder.

Loop modes map to `THREE.LoopOnce | LoopRepeat | LoopPingPong`; the mixer still advances in
`_loop` with real `dt`, plus `mixer.setTime(t)` on seek.

**`gltf-animation-pointer.ts`** (`packages/ui/src/viewer/`, next to `gltf-edge-extensions.ts`):
a `GLTFLoader` plugin registered once in `_initLoaders()` (:690). Its `loadAnimation(index)`
returns `null` for an animation without pointer channels, so the parser does its usual work
(plugins are asked first, `_invokeOne`, GLTFLoader.js:2805). Otherwise it takes the parser's own
clip for the node channels (`parser.loadAnimation(index)`, which skips channels without a node,
:4025) and adds, per pointer channel `/materials/{i}/pbrMetallicRoughness/baseColorFactor`, the
tracks three understands natively: a `ColorKeyframeTrack` named `<node>.material.color` (RGB,
linear in the file and in `material.color`) and a `NumberKeyframeTrack` `<node>.material.opacity`
(A), for every node whose mesh uses material `i` (`json.nodes` → `json.meshes[].primitives[]
.material`, the node by `parser.getDependency('node', n)`; names are unique after load,
`createUniqueName` :3655). From there the mixer does everything: `setTime()`, loop modes, and the
loaded colour and opacity come back when the action stops (AnimationMixer.js:152). About 100
lines, nothing for files without the extension, and the same route the edge extensions take for
what three does not know.

**`animation-playback.ts`** (free functions, like `instruct-playback.ts`) keeps what glTF and the
mixer cannot do: `depthWrite = opacity >= 1` on the fading materials the plugin listed (a `BLEND` material loads
with `depthWrite: false`, GLTFLoader.js:3581: right while it is translucent, wrong once it is
solid again); chapters as a lookup. Testable without a canvas, like `instruct-playback.test.ts`.

The viewer-menu dropdown (:173) stays as the quick switch and finally drives the
`activeAnimation` signal (`state/viewer.ts:16`), joined by `animationTime`,
`animationPlaying` and `animationsAvailable`.

#### `editor-animation-tool`

`packages/ui/src/editor/tools/animation-tool.ts`, registered in `editor.ts:61` as
`{ id: 'animation', icon: 'clapperboard', name: 'Animation', component: 'editor-animation-tool', width: 30, height: 50 }`.
Unlike the tools imported at `editor.ts:22-30`, its module is `await import()`ed when the tool is
first opened (`editor.ts:1074`): the element upgrades in place when its definition arrives, and
the editor bundle does not grow for people who never animate. Like the instruct tool it holds no
scene logic: it writes signals and calls the viewer's API.

1. **List.** Declared animations (from `state.animations`) and the presets, each with a
   checkbox "bake into the model". Picking presets makes the editor request
   `default/model/glb?animations=<declared + picked>` instead of the bare path in

   `thumbnails.glbOf()` takes whichever `default/model/glb…` output is there.
2. **Transport.** Play/pause, loop mode, speed, a scrubber with the chapters marked and the

3. **Options** of the selected preset (layout kind, spacing, order, stagger, duration, easing,
   turntable degrees) → a re-run with the option string in the path; the equivalent script

4. **Record** (§7). 5. **Download GLB** with the baked animations.

### 6. Parameter keyframes

`.param(name, values | { from, to, frames })`, several `.param()` calls advance together
(frame i takes the i-th value of each). Resolution in the run keeps the declaration
(`AnimationData.params.frames`); the rest happens in the host:

1. For each frame: run with `params` and request `default/model/glb?animations=false`
   (`runScript()` in the editor, serialised in the one worker; `runOnce()` in the CLI). The
   editor shows progress and stays usable; the thumbnails service already shows how to run in
   the background without disturbing the foreground.
2. `GLTFBuilder.addParamFrames(frames: Array<{ values, glb }>, data)` merges them into the
   first frame's GLB. Per scene path, by comparing the geometry across frames:
   - **unchanged** (same positions and indices): one copy, no channel;
   - **same topology** (same index buffer and vertex count, different positions): one mesh
     with a **morph target per frame** (POSITION and NORMAL deltas) and a `weights` channel —
     LINEAR, so a box whose width is the parameter morphs smoothly between frames (exact where
     the geometry depends linearly on the parameter, an approximation elsewhere). This is the
     common case for boxes and extrusions with a fixed ring, and gives a true continuous
     parameter animation from a handful of runs;
   - **different topology**: a **flipbook** — the frame's geometry nodes under the container,
     scale `1 ↔ 1e-4` by STEP keys (what the commented `sequence()` code at :164 did);
   - a part present in some frames only is a flipbook with the missing frames hidden.
   Node names, materials and the Archiyou extras come from the first frame. `extras.animations`
   gets the resolved frame times.
3. Where it runs: the merge is `GLTFBuilder`, so it runs in the worker through a new
   `RunnerWorker` method (`mergeAnimationFrames`) or on the main thread — core is isomorphic.
   CLI: `archiyou animate <file.js> [--animation widths] [--out anim.glb]`, the `sweepRuns()`
   loop with the frame values.

Costs, said before someone finds out: N runs of the whole script; a flipbook is N × the changed
geometry (a 24-frame flipbook of a 5 MB model is 120 MB), morph targets are N × positions of the
changed parts only. Default 12 frames, capped at 48, both overridable; the tool shows the size
before writing the file. Rigid-change detection (a part that only moved) is a later refinement
that turns a flipbook entry into pose keys.

### 7. The recorder

`renderModelAnimation(glb, data, options)` next to `renderModelThumbnail()` (:3293), with the
same shape — its own renderer, scene and lights, nothing leaking from the live viewer — and a
**fixed time step**: `t = i / fps`, `mixer.setTime(t)` (poses, colour, opacity), the extras
visibility and `depthWrite` at `t`, camera from the camera track, a turntable, or the live viewer's current view, then `render()` and read the
frame. The result is identical on a slow laptop and a fast one, which a recording from the
live canvas never is.

| Output | Encoder | For |
|---|---|---|
| WebM (VP9, alpha when the background is transparent) | WebCodecs `VideoEncoder` + a small muxer | websites, loops |
| MP4 (H.264) | WebCodecs where the browser has the codec | social platforms |
| GIF | a small quantising encoder in a worker, 15 fps | chats, READMEs |
| PNG sequence (zip) | the canvas, `fflate` | editing elsewhere |

WebCodecs is in Chrome, Edge, Safari (16.4+) and Firefox (130+); where it is missing the
recorder falls back to `MediaRecorder` on `canvas.captureStream()` in real time, and says so.
Muxer and GIF encoder are small, dependency-free libraries loaded on demand (candidates:
`mp4-muxer`/`webm-muxer`, `gifenc`) so the editor bundle does not grow; the choice is made
when stage 3 starts, with a note in `ATTRIBUTION.md`.

Options and the presets the Record panel offers:

- size: Square 1080×1080, Story 1080×1920, Landscape 1920×1080, custom; fps 30 (GIF 15);
- background: the view style's, a colour, or transparent (WebM/GIF/PNG);
- view style (`VIEW_STYLES`), grid off, edges as the style says;
- camera: follow the animation's camera, turntable over the clip, or the current view;
- loop count for GIF; duration from the animation; a progress bar and a download.

A step-by-step `assembly` recording drives the instruct player (ghosting, hiding, labels) at
fixed times, so the video shows what the viewer shows and not only what glTF can say.
