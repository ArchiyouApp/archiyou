## Signals: one small event bus in the server

### Context

In the previous Archiyou, scripts and outputs failed without anyone noticing. Today it is the same:
- a published configurator that fails in a visitor's browser only does `console.error` and a
  `postMessage` to the embedding page (`packages/ui/src/configurator/configurator.ts:300,339`);
- the API runs with `logger: false`; an unhandled 500 is only `console.error`'d (`apps/server/src/plugin.ts:288-295`);
- worker failures, Mailgun failures, translation failures, failed fulfillments: `console.*` or an
  author-only event, nobody on the team is told; failed BullMQ jobs vanish after 24 h.

Goal: one **signals bus** inside the API process. Everything that goes wrong (and a few things that
go right, for rates) is emitted as a *signal*; a **rules table in code** routes each type to
**Umami** (umami.archiyou.com, a new website "Archiyou platform"), to a **Postgres table** (the
truth for reports), and/or to an **email alert** to the team. A **daily email report** summarises
yesterday. Decisions taken: alerts by email via the existing Mailgun `EmailService`; rules in one
TS file; report by email; author-facing visibility later, not in this plan.

### Principles (simple + robust)

1. **Emitting never fails and never waits.** `signal(...)` is synchronous, swallows every error,
   returns nothing. A broken sink can never break a request, a run or a fulfillment.
2. **Postgres is the truth, Umami is best-effort.** Reports and alerts read our own table, so they
   work when Umami is down. Umami gets a bounded queue with a timeout; when full, drop and count.
3. **Aggregate, don't log rows.** One row per *fingerprint per day* with a counter. A burst of
   10 000 identical errors is one row and one upsert per flush.
4. **No new infrastructure.** No new container, no queue, no cron: in-process timers like the
   existing `purgeEvents` (`plugin.ts:204-215`). The worker stays isolated (no DB, no secrets):
   the API notices worker problems itself.
5. **Inert until configured.** No Umami URL → Umami sink off. No alert address → alerts/report go
   to the console. Development needs nothing.
6. **No loops.** Sinks never emit signals; a failing alert email is counted, not re-signalled.
7. **Privacy.** No IP stored (forwarded to Umami for sessions only, as the sites' `/t` proxy
   does); no script source (`ScriptStatementResult.code` can hold the whole script — never
   forwarded); params only as the configuration `query`; all strings capped.

### Shape

```
 configurator / editor (browser)                     API process (apps/server)
 ─────────────────────────────                       ─────────────────────────────────────────────
 services/signals.ts  ──sendBeacon──► POST /signals ─┐
   run.failed, output.failed,          (rate-limited,│
   configurator.view, app.crashed,      whitelist)   ▼
   execution.fallback                            signal(s) ──► rules.ts ──┬─► store   (signals table, upsert per fingerprint/day)
                                                    ▲                     ├─► umami   (POST umami.archiyou.com/api/send, queued)
 server emit points ────────────────────────────────┘                     └─► alert   (email to team, throttled)
   api.error, execution.failed, worker.down,
   fulfillment.failed, email.failed, …           daily timer ──► report.ts ──► email to team (once a day, claimed in DB)
```

#### The signal

```ts
// packages/types/src/signals.ts (shared by editor and server)
interface Signal {
  type: SignalType;                 // 'run.failed', 'api.error', ...
  source: 'configurator' | 'editor' | 'api' | 'worker';
  message?: string;                 // ≤ 300 chars
  script?: string;                  // 'author/name:version'
  scriptVersionId?: string;
  line?: number;
  query?: string;                   // configuration as a link query, ≤ 500 chars
  appVersion?: string;              // __APP_VERSION__ / server package version
  data?: Record<string, string | number | boolean>;  // ≤ 10 keys, short values
  user?: string;                    // handle of the signed-in user — SET BY THE SERVER ONLY
}
export const CLIENT_SIGNAL_TYPES = ['run.failed', 'output.failed', 'configurator.view', 'app.crashed', 'execution.fallback'] as const;
```

#### The user

A signal carries the handle of the signed-in user when there is one, so the team can see who was
affected and contact them. Anonymous visitors of a configurator have none.
- **Never taken from the body.** `POST /signals` ignores any `user` field; it reads the Bearer
  token when present and valid (`optionalUser()` exactly as `routes/feedback.ts`), else null. The
  client sender passes the token through `authService.getToken()` (sendBeacon cannot set headers,
  so with a token it uses `fetch(..., { keepalive: true })`; without one, sendBeacon).
- **Server signals** take `request.user?.sub` where a request is at hand (`api.error`, fulfillment
  routes); worker/broker signals take the job's caller when the job carries it, else none.
- **Not part of the fingerprint**: the same error for five users is one problem with five users.
- **Stored per aggregated row** as `users` (jsonb array of distinct handles, capped at 20) plus
  `user_count`; the alert and the report show "affected: 3 users (alice, bob, carol)".
- **Not sent to Umami.** Umami stays anonymous analytics; who was affected lives only in our own
  table and is gone after `retentionDays` (90).

#### The rules (`apps/server/src/signals/rules.ts`)

One table keyed by type — that *is* the routing. Unknown types are refused at the route and
dropped (with a count) on the server.

| type | from | severity | store | umami | alert |
|---|---|---|---|---|---|
| `configurator.view` | client | info | – | ✓ (tag = `author/name`) | – |
| `run.failed` (published configurator run) | client | error | ✓ | ✓ | – (digest) |
| `output.failed` (fulfillment/export/project output in the browser) | client | error | ✓ | ✓ | – |
| `app.crashed` (window error / unhandledrejection, same-origin only) | client | error | ✓ | – | – |
| `execution.fallback` (server run refused → local kernel, `execution-service.ts:412`) | client | warn | ✓ | – | – |
| `api.error` (unmapped 500, `plugin.ts:294`) | api | error | ✓ | – | ✓ new fingerprint |
| `execution.failed` (job failed / timed out, `ExecutionBroker.ts:105`) | api | error | ✓ | ✓ | – |
| `execution.unavailable` (pipeline down at boot, `plugin.ts:183`) | api | critical | ✓ | – | ✓ |
| `worker.down` (no BullMQ worker alive while an execution gate is open) | api | critical | ✓ | – | ✓ hourly max |
| `fulfillment.failed` (`routes/fulfillments.ts:234`, a customer is affected) | api | error | ✓ | ✓ | ✓ new fingerprint |
| `email.failed` (`EmailService.ts:266,269`) | api | error | ✓ | – | **never** (would loop) |
| `translation.failed` (`TranslationQueue.ts:83`) | api | warn | ✓ | – | – |
| `maintenance.failed` (event purge etc., `plugin.ts:210`) | api | warn | ✓ | – | – |

Per rule: `alert: { when: 'new' | 'always', throttleMinutes }` and optional `fingerprint(signal)`;
default fingerprint = sha256(type + script + normalised message (digits → `#`, trimmed) + line),
24 hex chars like `EventStore.configurationKey`. Editor runs of a script being *edited* are never
signalled — those errors are normal work.

### Files

#### New, server — `apps/server/src/signals/`
- `rules.ts` — the table above, typed against `SignalType`.
- `bus.ts` — `signal(s)`: validate/cap fields, look up rule, fan out to sinks inside try/catch.
  Holds a small in-memory aggregate `Map<fingerprint, {count, first sample}>` (capped at 1 000
  keys), flushed to the store every 10 s and on `onClose`. Counters for dropped/failed per sink
  (read by the report). `startSignals(fastify)` registers the flush timer, the report timer and
  the worker-liveness check, all `.unref()` and cleared in `onClose` like `purgeTimer`.
- `SignalStore.ts` — upsert `INSERT … ON CONFLICT (fingerprint, day) DO UPDATE SET count = count + $n, last_seen = now()`;
  `isNew(fingerprint)` (no earlier day); `day(d)` rows for the report; `purge(retentionDays)`;
  `claimReport(day)` (see report).
- `umami.ts` — bounded queue (500), concurrency 2, 3 s timeout, `POST {SERVER_UMAMI_URL}/api/send`
  with `{ type: 'event', payload: { website, hostname: 'next.archiyou.com', url, name, data, tag } }`.
  Client signals forward the visitor's `User-Agent` and `X-Forwarded-For` (the API has
  `trustProxy: true`), like `archiyou-sites/src/app/(frontend)/t/api/send/route.ts`; server
  signals send a fixed UA `archiyou-server/<version>`. Umami event names keep the sites' style:
  `run.failed` → `configurator-error`, `configurator.view` → `configurator-view`, others as is.
- `alerts.ts` — `alert(signal, row)`: throttle per fingerprint (in memory) + global cap
  (`SERVER_SIGNALS_ALERT_MAX_PER_HOUR`, default 10, then one "N more alerts suppressed" line in the
  report). Sends through `emailService.sendTeamAlert`.
- `report.ts` — `sendDailyReport(day)`: yesterday's (UTC) rows: **new problems** (first seen that
  day), **top recurring** by count, totals per source, sink health (dropped/failed counts,
  suppressed alerts) and, when Umami is configured, `configurator-view` vs `configurator-error`
  per script from `GET /api/websites/:id/events/stats` (same endpoint the sites use in
  `src/lib/analytics/umami.ts:121`) → failure rate. Sent **every day, also when quiet** ("all
  quiet, 0 problems"): that mail is the heartbeat that proves monitoring itself works.
  Idempotent: `claimReport(day)` inserts a `signals` row with type `report.sent` using
  `ON CONFLICT DO NOTHING RETURNING`; only the caller that gets the row sends. Timer checks hourly;
  sends once the hour ≥ `SERVER_SIGNALS_REPORT_HOUR` (UTC, default 6).

#### Admin: a "Signals" section (operator screen `/admin/signals`)

The same pattern as the feedback inbox, read-only.
- **Server:** `GET /admin/signals` in `routes/admin.ts` (behind `adminOnly`, like `/admin/feedback` at
  line 128). Query parameters:
  - `q`: search in message, script and user (ILIKE)
  - `type`, `source`, `severity`
  - `range`: `today | 7d | 30d | 90d`
  - `sort`: `last | count | first`
  - `limit` / `offset`

  It returns rows grouped by fingerprint over the range: summed `count`, `first_seen`, `last_seen`,
  distinct `users` and `user_count`, the latest `sample`, and `new` (first seen inside the range).
  It also returns the totals per severity for the range, plus the list of types present (to fill the
  filter). It lives in `SignalStore.list(filter)`.
- **Client service:** `apps/editor/src/services/admin.ts` gets `fetchAdminSignals(filter)` and the
  `AdminSignal` type, next to `fetchAdminFeedback` (line 119).
- **Component:** `packages/ui/src/admin/admin-signals.ts`, modelled on `admin-feedback.ts`
  (same `fmtDate`, `PAGE_SIZE`, bar layout and Web Awesome components):
  - The filter bar has a search `wa-input` and `wa-select`s for range, severity, source and type, plus
    a sort. Above the table sits a row of counts per severity.
  - The table shows severity, type, the script (linked to its configurator), the message (truncated),
    count, users, first seen and last seen, with a "new" badge.
  - Clicking a row opens the sample: the line, the configuration `query` as a link to the
    configurator with those params (so it can be reproduced), the app version, `data`, and all
    affected users.
  - Nothing is editable. Resolve or mute can come later if the list gets noisy.
- **Page:** one entry in `_sections()` of `apps/editor/src/pages/admin.ts` (id `signals`, icon
  `activity`), plus its import.
- The alert and report emails link to `/admin/signals?range=…` (in the button), so a mail leads
  straight into the table.
- The component follows AGENTS.md: render first, then state, lifecycle, methods and styles; Allman
  braces; design tokens; no inline styles.

## Review and decisions by the human

- Asked for approaches first; rejected a separate error service in favour of reusing the configurator's host events, then of routing to the team's own Umami.
- Decided: alerts by email (Mailgun), rules in one file in code, daily report by email, authors' visibility later.
- Asked to add the signed-in user to a signal, and a table of signals with filters and search in the admin screen.

Changes to the plan during the work (by the agent, to be reviewed):

- No `user_count` column: a row keeps up to 20 distinct users per day, and the screens show "and N more" / "…" instead of a count that would be wrong past 20.
- `execution.failed` only for runs that never came back (job failed, timed out, worker died). A script's own error on a server run is already reported by the configurator as `run.failed`, so signalling it on the server too would count it twice.
- The failure rate per configurator in the report needs an Umami API key (`SERVER_UMAMI_API_KEY`); without one that section says so.
- Runner errors arrive as a formatted block that quotes lines of the script. Only the error itself is kept (`errorOnly`, browser and server), so no script code reaches the table, Umami or a mail.
- Umami drops events whose User-Agent looks like a bot (a plain `node` agent was dropped in a test); server signals send `Mozilla/5.0 (compatible; Archiyou/<version>)`, which it accepts.

Tested by the agent: server unit tests (28 files, 413 tests, of which 4 files and 28 tests new), editor tests (160, 5 new), typechecks of server and editor. End to end on separate ports with a throwaway local database (not the shared one) and the archiyou-sites development Umami: an anonymous visitor's failed run in a published configurator reached the `signals` table and Umami with script, line and configuration; a signed-in page's crashes arrived with the user; a user named in the body was ignored; the admin Signals section listed, filtered (also from the address) and opened a problem with a working "Open this configuration" link; `pnpm admin:signals report` and `alert-test` printed as expected. Not tested: a real Mailgun send, the daily timer over a real day, `worker.down` against a stopped worker, and the server's `api.error` from a real failing route (covered by the unit tests of the bus only).
