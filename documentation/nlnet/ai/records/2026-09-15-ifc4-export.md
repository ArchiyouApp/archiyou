### Plan: implement IFC_AUTO milestone 1 — classifier setup + housetest validation

#### Context

`plans/IFC_AUTO.md` (written last turn) designs an automatic IFC classifier: one entity-centric table `IFC_ENTITIES` with `hosts / name / shape / children / subclass` predicates, a small engine that walks the scene top-down, and `explainIfc()` as the human view. The user now asks to implement it, **focusing on setup and a first validation against the housetest script**, then pause so they can check the result. So this milestone stops at a readable classification of the real house; the `.is()` API and the IFC4/IFCX serializers are later milestones.

Established facts this plan builds on (verified in source):

- Rule engine to reuse: `Classification`, `ClassificationRule`, `classify()`, `RecipeReport` in `packages/core/src/modeler/Recipe.ts:1245-1400`.
- Kernel-agnostic OBB precedent: `Make.partList` classify at `packages/core/src/modeler/Make.ts:1601-1634`.
- House harness: `packages/core/tests/unit/runner/house.production.test.ts:36-64` (`fixtureData`, `fixture`, `runHouse` with `linkComponentScripts`); the default scope stays reachable after a run through `runner.getScope('default')` (`Runner.ts:593`), so the test can classify the live scene without adding an output format.
- Units: `MM_PER_UNIT` in `packages/core/src/units/UnitConverter.ts:21`; user channel `console.user()` at `packages/core/src/console/Console.ts:193`.

#### Scope of this milestone

In: `IFC4Exporter.ts` sections 1–3 (types, `TUNING`, `IFC_ENTITIES`, engine, `explainIfc`, report), a script/editor entry point to print the explanation, synthetic feature tests, the housetest validation test with a checked-in feature dump and explanation snapshot, and the pointer line in `plans/IFC4.md`.

Out (later milestones, per IFC_AUTO.md sequencing): `.is()`/`.isA()` API in `shapeAnnotations.ts` (the engine already *reads* `shape.metadata.is` and `node._is` so it works the day the API lands), timberfloor/urhousesketch/strawwall fixtures, BuildingModel IR, SPF/GUID, IFC4 and IFCX serializers, editor menu, scene-explorer badges.

#### Implementation

##### 1. `packages/core/src/modeler/IFC4Exporter.ts` (new, flat, TOC comment at the top)

**Section 1 — spec (the human-facing part)**
- Types: `IfcEntity`, `EntityRule`, `NodeName`, `ShapeFeatures`, `ChildrenFeatures`, `Ctx`, `FeatureNode` (`{ path, name, isLayer, isComponentRoot, componentRef?, explicit?, features?: ShapeFeatures, children: FeatureNode[] }`).
- `TUNING` with the constants and per-constant comments from IFC_AUTO.md.
- `NAME_STOPWORDS` (index/position tokens) used by `tokeniseName`.
- `IFC_ENTITIES` in precedence order, full entries for: IfcBuildingStorey, IfcRoof, IfcWall, IfcSlab, IfcFooting, IfcBuildingElementPart, IfcCovering, IfcBeam, IfcMember, IfcColumn, IfcPlate, IfcOpeningElement, IfcWindow, IfcDoor, IfcMechanicalFastener; `hosts + name` only for IfcStair, IfcRamp, IfcRailing, IfcChimney, IfcShadingDevice, IfcFurniture, IfcDiscreteAccessory, IfcPile; fallbacks IfcElementAssembly and IfcBuildingElementProxy. `ifc: { pset, qto, uri }` filled per entity.

**Section 2 — engine**, split so the expensive part and the decision part are separate:
- `tokeniseName(raw, componentRef?)` → `NodeName` (camelCase/`_`/space/`.` split, stopwords dropped, plural strip, head = last token).
- `shapeFeatures(shape, units)` → `ShapeFeatures | null`: `type` → kind; hidden from `style.visible`; extents/axes from `recipeOf()`+`asCuboid()` if live, else `obbox()` (mesh `axes()/halfExtents()`, brep `xDir/yDir/zDir` + `width/depth/height`), sorted `[t,w,l]`; `longDir/thinDir` from angle to Z with `TUNING` bands; `class`; `fill = volume / (t·w·l)`; `isBox`; `material().group`; `bbox` min/max as plain arrays. Plain JSON-serialisable on purpose.
- `buildFeatureTree(root: SceneNode, units)` → `FeatureNode`: walks `children()`, uses `SceneNode.path()`, detects component roots by the common `<ref>_` prefix of descendants, reads `node._is` / `shape.metadata.is` into `explicit`.
- `classifyTree(tree: FeatureNode, opts)` → `IfcClassification { nodes: Map<path, Classification>, storeys, conflicts, duplicates, skipped, collapsed, report }`. **Pure over the feature tree**, no scene access, so tests run in milliseconds on a dump. Internals: `childrenFeatures()` (aggregate measured in the dominant-stick frame), structural rules (empty, wrapper collapse, transparency, group), `resolve()` exactly as specified in IFC_AUTO.md, storey synthesis, host-relative leaf features (`plane`, `touches`, `relLength`, `alongDominant`, `insideHost`, `spansOpening` against hidden `opening*` polygons in the same host), leaves compiled to `ClassificationRule`s and run through `classify()` with `{kind:'baked', reason:'classifier'}` as root, post-checks (duplicates, conflicts, proxies).
- `classifyScene(root, { units })` = `classifyTree(buildFeatureTree(root, units), …)`.

**Section 3 — views**
- `explainIfc(result, tree)` → text tree in the format shown in IFC_AUTO.md: runs of identical siblings collapsed (`stud0..stud8, endstud ×10`), `!!` for conflicts/duplicates, footer with skipped/proxies/conflicts/duplicates counts.
- `ifcHistogram(result)` → `Record<'IfcMember.STUD', number>` for contract tests.
- Report lines through `RecipeReport` where it fits; otherwise a plain `summary()` string.

### Exporter: the agent's answer of 13:44, approved with the decisions of 13:47

Classification is done; the file itself is not. Nothing yet writes IFC, and there is no STEP file writer to reuse: the only STEP output path calls an old exporter, and no GUID helper exists. The rest of the work follows `plans/IFC4.md` Parts 2 to 4, in this order:

1. **Building model.** Turn the classification into a format-neutral model: project, site, building and storeys, then every product with its entity, type and parent. The classifier only sees measurements, so this step reconnects each product to its live shape by scene path. Shapes from the brep kernel need tessellating first.

2. **IFC relationships.** Parts such as studs, plates and insulation go *into* their wall or roof. Walls, the roof, doors and windows go *into* the storey. An opening cuts its wall, and a door or window fills an opening. IFC allows each element only one parent, so this needs its own tests.

3. **Geometry.** Each part gets a face-set body in world coordinates, keeping n-gons, reusing the approach in `DAEExporter.ts`. Openings currently have no body; they need their rectangle extruded through the wall thickness. The roof and framed walls get no body of their own, since their parts carry the geometry.

4. **Properties and quantities.**
   - **Standard property sets:** the common set for each entity, such as `Pset_WallCommon`.
   - **Quantities:** volume, area and weight.
   - **Materials:** where the script sets them.
   - **An Archiyou property set:** the scene path, the classification evidence and embodied carbon.

5. **File writer.** Three parts:
   - A small writer for the text format (ISO 10303-21): numbered entities, references, string escaping, enums and the header.
   - Deterministic 22-character GUIDs derived from scene paths, so re-exports stay comparable.
   - The IFC4 serializer itself: units, representation context, owner history, placements, bodies and the relationships above.

6. **Wiring.** Add an `ifc` model format to the constants, types and Runner output switch, plus `Modeler.toIFC()`. In the editor, add an IFC entry to the export formats and the File ▸ Export menu, plus the format lists in the publish and fulfillment code.

7. **Validation.**
   - A structure test: every reference resolves, GUIDs are unique, and every product has exactly one parent.
   - A read-back test with `web-ifc` as a dev dependency.
   - Opening the exported housetest in BlenderBIM or another IFC viewer.

8. **The `.is()` override API.** It is not needed for a first file. It is needed as soon as a guess is wrong, and for tagging storeys explicitly. The classifier already reads these tags.

Items 1 to 5 are the bulk of the work. Wiring is small once `toIFC()` exists.

**Decisions to settle before building:**
- **Offcuts:** the opening cuts split insulation into 30 small pieces. Export each as a part, or merge them per wall?
- **Duplicates:** skip the mirrored ridge purlin, or export it and report it?
- **Unfilled openings:** the front opening would be exported as a hole with nothing in it. Is that acceptable?
- **Geometry:** use plain face sets only for the first version? Extrusions derived from recipes would give cleaner, editable elements in BIM tools, but they can come later.

**Validated so far on a real model:** walls, framing, insulation, the roof, openings and windows. The slab, footing, covering, sheathing and door rules have no real-model check yet. Adding the `timberfloor` and `urhousesketch` scripts to the corpus would cover most of them.
